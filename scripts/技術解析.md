# 技術解析：這個啟動器是怎麼「選到帳號」的

> 對象：想知道原理、或之後要自己維護／修改這支工具的人。
> 目標程式：三國神燈（台服版）V3.0.0.25，`SanOLLamp.exe`

---

## 一句話版本

神燈是一支 **MFC 對話框程式**，所有欄位都是標準 Win32 控制項，各自有固定的
數字 ID。所以不需要模擬滑鼠點擊螢幕座標，而是**直接對那些控制項送 Win32 訊息**
—— 等於繞過畫面，直接跟程式的 UI 層對話。

```
啟動 SanOLLamp.exe（不提權）
        │
        ├─ 等主視窗出現（class = #32770）
        │
        ├─ CB_SHOWDROPDOWN  → 逼帳號下拉載入清單（它是懶載入的）
        ├─ CB_GETLBTEXT     → 讀出 15 個帳號名稱，比對出目標的索引
        ├─ CB_SETCURSEL     → 選到該索引
        ├─ WM_COMMAND       → 補送 CBN_SELCHANGE 通知，觸發程式的處理常式
        │                     ↑ 少了這步，選了等於沒選
        ├─ WM_GETTEXT       → 讀「遊戲路徑」確認真的生效了
        │
        └─ CB_SETCURSEL + WM_COMMAND → 同樣手法選「設置」
```

---

## 一、為什麼不用模擬滑鼠

模擬座標點擊（`SetCursorPos` + `mouse_event`）有幾個致命問題：

* 視窗位置會變、DPI 縮放會變、解析度會變 —— 座標全部失效
* 多開時每個視窗位置不同，要先算出每個視窗的座標
* 會搶走使用者的滑鼠，執行期間不能碰電腦
* 下拉選單展開後的項目位置要再算一次，還要考慮捲動

送訊息沒有這些問題：**控制項 ID 是編譯進程式的常數**，視窗在哪、有沒有被遮住、
有沒有最小化，都不影響。

---

## 二、怎麼知道有哪些控制項

用 `EnumWindows` 找出屬於 `SanOLLamp.exe` 的頂層視窗，再用 `EnumChildWindows`
把子控制項全部列出來，每個印出 class name、文字、以及 `GetDlgCtrlID` 回傳的 ID。

實際掃出來的結果（29 個子控制項，以下是有用到的）：

| ID | 類型 | 畫面上的名稱 |
|---|---|---|
| 1000 | Button | 啟動遊戲 |
| 1001 | Edit | 帳號欄 |
| 1005 | Edit | 遊戲路徑 |
| 1012 | Static | 狀態列 |
| **1019** | **ComboBox** | **遊戲帳號** |
| 1021 | Edit | 登錄密碼 |
| 1024 | Edit | 保護密碼 |
| 1025 | Button | 自動登錄,讀取 |
| 1026 | ComboBox | 伺服器（5 項）|
| 1027 | ComboBox | 分流（2 項）|
| 1029 | ComboBox | 角色（3 項）|
| 1030 | Button | 進遊戲掛機 |
| 1032 | Button | 自動重啟 |
| **1033** | **ComboBox** | **設置（20 項）** |

主視窗的 class 是 `#32770`，這是 Windows 對話框的標準類別名稱 —— 看到這個就
知道可以用 `GetDlgItem(hwnd, id)` 直接拿到控制項的 handle。

## 三、三個會讓你以為「程式壞了」的坑

這三個全都是**靜默失敗**：不會丟例外、不會有錯誤碼，只會回傳 0 或空字串。
debug 時很容易誤判成「神燈沒反應」或「欄位本來就是空的」。

### 坑 1：提權的實例，訊息完全送不進去

神燈的 manifest 寫了 `requestedExecutionLevel = highestAvailable`。在管理員帳號
下手動雙擊，Windows 會把它提權（所以每開一個就跳一次 UAC）。

而 **UIPI（User Interface Privilege Isolation）** 規定：低完整性等級的行程不能
對高完整性等級的視窗送訊息。一般權限的腳本送訊息給提權的神燈，**訊息會被系統
默默丟掉，`SendMessage` 回傳 0**。

實測對照：

| 目標實例 | `CB_GETCOUNT` 於 1026（伺服器）|
|---|---|
| 手動雙擊開的（提權）| `0` ← 被擋 |
| 腳本用 RunAsInvoker 開的 | `5` ← 正常 |

**解法**：啟動前設環境變數 `__COMPAT_LAYER=RunAsInvoker`，讓子行程以呼叫者的
權限執行。

```powershell
$env:__COMPAT_LAYER = 'RunAsInvoker'
Start-Process $ExePath -WorkingDirectory (Split-Path $ExePath -Parent)
Remove-Item Env:\__COMPAT_LAYER
```

這個做法只影響啟動的子行程，不修改 UAC 設定、不寫登錄檔。附帶好處是**不會再跳
UAC 提示**。

> 所以「不跳 UAC」和「自動化能動」其實是同一件事的一體兩面。
> 如果你自己另外用「以系統管理員身分執行」開了神燈，本工具碰不到那些視窗。

前提是遊戲目錄一般權限要可寫（已驗證 `C:\Game\SanOLLampTW_Unity\` 與其
`config\` 都可寫），否則不提權會有別的問題。

### 坑 2：帳號下拉是懶載入

剛啟動的神燈，`CB_GETCOUNT` 對 1019 回傳 **0**。不是因為沒帳號，而是它要等到
使用者**展開下拉時**才去掃 `config\` 填清單。

```powershell
# 展開前
SendMessage($cbo, CB_GETCOUNT, 0, 0)   # -> 0

SendMessage($cbo, CB_SHOWDROPDOWN, 1, 0)
Start-Sleep -Milliseconds 500

# 展開後
SendMessage($cbo, CB_GETCOUNT, 0, 0)   # -> 15
```

讀完記得送 `CB_SHOWDROPDOWN` 搭配 `wParam = 0` 收起來。

### 坑 3：跨行程讀字串，別自己做 ReadProcessMemory

直覺的做法是「在目標行程配置記憶體 → 送訊息叫它寫進去 → 讀回來」：

```powershell
# 這樣是錯的，而且不會報錯
$rem = VirtualAllocEx($hProc, 0, 2048, MEM_COMMIT, PAGE_READWRITE)
SendMessage($ctl, WM_GETTEXT, 512, $rem)
ReadProcessMemory($hProc, $rem, $buf, 2048, [ref]$read)   # 回傳 True，但內容全是 0
```

`ReadProcessMemory` 會**回傳成功**，讀到的卻是空的。原因是 Windows 對
`WM_GETTEXT` 這類訊息本來就會自動做跨行程 marshalling —— 它根本沒有把資料寫到
你配置的那塊記憶體。

正確做法是直接傳 `StringBuilder`，讓系統自己處理：

```csharp
[DllImport("user32.dll", CharSet=CharSet.Unicode, EntryPoint="SendMessageW")]
public static extern IntPtr SendSb(IntPtr h, uint msg, IntPtr w, StringBuilder l);
```

```powershell
$sb = New-Object Text.StringBuilder 1024
SendSb($ctl, WM_GETTEXT, 1024, $sb)
$sb.ToString()        # -> 'C:\USERJOY\SGO\Exe\'
```

實測三種讀法的對照：

| 讀法 | 主視窗標題 | Edit 1005 內容 |
|---|---|---|
| `GetWindowTextW` | 讀得到 | **讀不到**（跨行程時只回傳快取的標題，子控制項是空的）|
| `SendMessage` + `StringBuilder` | 讀得到 | **讀得到** |
| `VirtualAllocEx` + `ReadProcessMemory` | 空字串 | 空字串 |

`CB_GETLBTEXT`（讀下拉項目）同樣用 `StringBuilder` 就可以。

## 四、選帳號的完整流程

### 4.1 為什麼 CB_SETCURSEL 不夠

`CB_SETCURSEL` 只改下拉的「目前選取項」，它**不會通知父視窗**。MFC 程式真正做事
的地方在 `ON_CBN_SELCHANGE` 處理常式 —— 那是收到 `WM_COMMAND` 才會跑的。

所以只送 `CB_SETCURSEL` 的話，畫面上看起來選好了，但程式完全不知道，
遊戲路徑、伺服器、設置都不會更新。必須自己補送通知：

```powershell
# 1. 改選取項
SendMessage($cbo, CB_SETCURSEL, $index, 0)

# 2. 補送 CBN_SELCHANGE 給父視窗
#    wParam = MAKEWPARAM(控制項ID, 通知碼)，lParam = 控制項 handle
$wParam = [IntPtr](($CBN_SELCHANGE -shl 16) -bor $CtrlId)
SendMessage($mainWindow, WM_COMMAND, $wParam, $cbo)
```

按鈕同理，用通知碼 `BN_CLICKED`（= 0）：

```powershell
$wParam = [IntPtr](($BN_CLICKED -shl 16) -bor 1000)   # 1000 = 啟動遊戲
SendMessage($mainWindow, WM_COMMAND, $wParam, $btnHandle)
```

### 4.2 選了帳號之後，神燈做了什麼

選到 `teddy810`（索引 13）之後的實測結果：

```
CB_GETCURSEL      = 13
下拉顯示文字       = 'teddy810'
遊戲路徑 (1005)   = 'C:\USERJOY\SGO\Exe\'   ← 自動帶出來
伺服器 (1026)     = index 2                 ← 自動對上
```

因為神燈去讀了 `config\teddy810\login.ini`，把裡面的設定灌進整個表單：

```ini
[GameSet]
GameRoot=C:\USERJOY\SGO\Exe\     ← 填進「遊戲路徑」
AutoLogin=1
AutoStart=0
ReStart=1
Server=2                          ← 選到「伺服器」的第 2 項
Mirror=1                          ← 「分流」
Role=0                            ← 「角色」
[Player]
LoginId=teddy810
PassData=<64 字元，已編碼>         ← 密碼，腳本全程不碰
[SettingUse]
Value=1                           ← 「設置」
[SettingName]
Name0=設置1
Name1=設置2
...
Name19=設置20                     ← 下拉固定 20 項就是這裡來的
```

**所以「選帳號」等於「載入該帳號的整份設定」**。腳本不需要、也沒有去碰密碼欄
（1021 / 1024）—— 密碼本來就存在 `login.ini` 裡，選帳號時神燈自己會填。

### 4.3 索引怎麼對應到帳號

下拉的順序 = `<神燈目錄>\config\` 底下子資料夾的順序，已逐一比對確認一致：

```
config\                      下拉索引
├── changer1          ←→     [0]
├── changer1234       ←→     [1]
├── changer12345      ←→     [2]
├── jjkl123456        ←→     [3]
├── microjet1         ←→     [4]
...
└── teddy8650         ←→     [14]
```

這就是為什麼 GUI 可以**瞬間**列出帳號清單 —— 它直接讀資料夾，不用先開一個
神燈實例去問。但真正要選的時候，腳本還是會**重新讀一次下拉的實際內容**再比對
名稱，不會盲目相信索引：

```powershell
$list = Get-LampAccounts -Main $h          # 從下拉實際讀回來
$idx  = [Array]::IndexOf($list, $acct)     # 用名稱比對
if ($idx -lt 0) { ...放棄這個視窗... }
```

這樣就算哪天神燈改了排序規則，也不會選錯帳號。

## 五、「設置」為什麼要逐帳號分開

下拉（1033）**永遠是 20 項**，不管該帳號實際上有沒有那些設置檔。選到一個不存在
的設置，等於套用一份空設定。

所以 GUI 只列出該帳號真的有的：掃 `config\<帳號>\Setting*.ini`。

```
teddy810    → Setting1~8.ini      → 下拉顯示「原本設置 + 設置1~設置8」
teddy333    → Setting1~17.ini     → 「原本設置 + 設置1~設置17」
changer1    → Setting1,2,4,6.ini  → 「原本設置 + 設置1,2,4,6」（跳號）
microjet1   → 沒有任何設置檔       → 只有「原本設置」，欄位鎖定
```

索引換算：**`設置N` 對應下拉索引 `N-1`**（依據 `login.ini` 的
`Name0=設置1`）。

> ⚠️ **選了設置會改到檔案。** 神燈在選擇後會把整份 `login.ini` 重寫，
> `[SettingUse] Value` 就被改掉了。這是神燈自己的行為，不是本工具寫的。
> 不想更動就保持「原本設置」—— 那一列腳本完全不碰 1033。

## 六、失敗了怎麼辦：每一步都驗證

腳本不假設任何一步會成功，每個環節都檢查，失敗就**跳過這個視窗繼續下一個**，
不會把錯誤累積下去：

| 檢查點 | 判斷方式 | 失敗時 |
|---|---|---|
| 行程有起來 | 比對啟動前後的 PID 清單，最多等 20 秒 | 記錄「啟動失敗」 |
| 主視窗出現 | 輪詢 `EnumWindows` 找 class `#32770`，最多等 25 秒 | 記錄「找不到視窗」 |
| 帳號在清單裡 | `IndexOf` 回傳 ≥ 0 | 記錄「不在神燈清單中」 |
| 選取成功 | 回頭讀 `CB_GETCURSEL` 是否等於目標索引 | 記錄「選帳號失敗」 |
| **真的生效** | 讀「遊戲路徑」(1005) 是否非空 | **中止這個視窗的後續動作** |
| 設置選取 | 同樣回讀 `CB_GETCURSEL` | 記錄但繼續（不致命）|

其中最關鍵的是**讀遊戲路徑**那一步。它是整條鏈路的「驗證點」：路徑有值，就證明
`CBN_SELCHANGE` 確實被處理了、`login.ini` 確實被讀進去了。如果這裡是空的，代表
前面某個環節默默失敗了，這時候絕對不能繼續往下按「啟動遊戲」。

## 九、沒有做的事

誠實交代範圍：

* **「啟動遊戲」按鈕（1000）沒有實際測試過。** 按下去就是真的登入，開發過程中
  沒有在未經同意的情況下觸發。它用的是跟下拉選單同一套 `WM_COMMAND` 機制，
  那套已驗證可用，但按鈕本身未經實測。預設是**不按**的，要勾選才會執行。
* **密碼欄位（1021 / 1024）完全沒有碰**，不讀也不寫。
* **伺服器 / 分流 / 角色（1026 / 1027 / 1029）沒有提供覆寫**，一律沿用
  `login.ini` 帶出來的值。要加的話機制跟「設置」完全一樣，照 4.1 的方式送
  `CB_SETCURSEL` + `CBN_SELCHANGE` 即可。
